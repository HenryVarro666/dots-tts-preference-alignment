## A. 环境与依赖类错误

### A-1 · setuptools 扁平布局打包失败 — `74f01de`
- **现象**：`bash env/setup_env.sh` 的 `[3/6] pip install -e .` 报
  `error: Multiple top-level packages discovered in a flat-layout: ['eval','data','pairs',...]`。
- **根因**：本项目用 `sys.path.insert` + `from common import ...` 的脚本组织，**不是一个可安装的 Python 包**；但 setuptools 看到一堆顶层目录（`eval/` `data/` …），以为要把它们都当包打进去，自动发现失败。
- **修复**：在 `pyproject.toml` 显式声明「无包、无模块」，关闭自动发现：
  ```toml
  [tool.setuptools]
  packages = []
  py-modules = []
  ```
  顺带把弃用的 `license = {text=...}` 改成 SPDX 字符串 `license = "Apache-2.0"`。
- **为什么这么修**：我们 `pip install -e .` 的**唯一目的是装增量依赖**（jiwer/peft/…），不需要把项目本身当包导入；声明空包是最干净、最不易误伤的做法（比 `src-layout` 重构成本低）。
- **教训**：扁平多目录 + 想用 `pip install -e .` 只装依赖时，**必须显式声明 packages/py-modules**，否则 setuptools 自动发现会炸。

### A-2 · speechmos 版本号不存在 — `d2ca012`（后被 #8 取代）
- **现象**：`ERROR: Could not find a version that satisfies the requirement speechmos>=1.0.0 (from versions: 0.0.1, 0.0.1.1)`。
- **根因**：我臆测了版本号；speechmos 在 PyPI 最新只有 `0.0.1.1`。
- **修复（当时）**：`speechmos>=1.0.0` → `>=0.0.1`。
- **后续**：见 **B-3** —— 这个包**根本不含 UTMOS**，最终被彻底移除。
- **教训**：**依赖的版本与 API 都要核实**，不能凭记忆写 `>=1.0.0`（呼应仓库总规范「外部信息先核实再用」）。

### A-3 · 重连/新 tmux 后忘激活 venv，误用 anaconda base（**真根因**）
- **现象**：`run_full_dataprep.sh` 候选生成 → `import dots_tts.runtime` 先报 `No module named 'librosa'`，补完又报 `No module named 'loguru'`（打地鼠），最后 `python -c` 自检报
  `torchaudio ... undefined symbol: torch_library_impl`。**此前候选生成/score_utmos/score_sim 都好好的**。
- **定位线索（关键）**：最后那个报错路径是 **`/home/exx/anaconda3/lib/python3.11/site-packages/torchaudio/...`** —— 不是 `.venv/...`。
  说明当前 shell 在 **anaconda base**，不在项目 venv。
- **根因**：**用户重新连接 SSH / 新开 terminal（或新建 tmux 会话）后，shell 默认回到 anaconda base，没 `source .venv/bin/activate`**。
  base 里没装 dots.tts 的依赖（loguru/librosa…），且 base 的 torch/torchaudio 版本不匹配（`undefined symbol`）→ 一连串"缺模块/动态库报错"。
  之前能跑，是因为那时在 venv 里。（我一开始误判为"pip 依赖被顶掉"，其实是**跑错环境**。）
- **修复**：① `source /data/dots-tts-preference-alignment/.venv/bin/activate` 回到 venv，`which python` 必须是 `.venv/bin/python`；
  ② `run_full_dataprep.sh` 顶部加**自动激活 venv**（新 tmux/终端直接跑也不会再误用 base）；
  ③ 顺带把 `librosa`/`soundfile` 写进 pyproject 作护栏（无害，但**不是本坑的根因**）。
- **教训（重要）**：
  - **tmux 会话 / 新终端不会自动继承 venv**——每次都要 `source .venv/bin/activate`（或让脚本自激活）。
  - 报错路径里出现 `anaconda3/site-packages` 而非 `.venv/site-packages` = 第一时间怀疑"跑错环境"，别急着 pip install。
  - **不要在没激活 venv 时 `pip install`**——会把包装进 base、污染 base（本次就把 base 的 numpy/torchaudio 搞乱了，幸好我们不用 base）。

### A-4 · `+` 不是 bash 的命令连接符（操作小坑）
- **现象**：`source .venv/bin/activate + git pull` 后报 `run_train_all.sh: No such file or directory`。
- **根因**：bash 里 `+` 不连接命令——`source .venv/bin/activate + git pull` 把 `+`、`git`、`pull` 当成 `source` 的参数，**`git pull` 根本没跑**，所以新文件没拉下来（`ls` 里有旧文件、没新文件 = 仍在旧 commit）。
- **修复**：分两行，或用 `&&`：`source .venv/bin/activate && git pull`。
- **教训**：连续命令用 `&&`（前一条成功才跑下一条）或分行；`git pull` 后 `ls <新文件>` 确认真的拉到了。

## B. 运行时报错（真问题）

### B-1 · 缺 whisper 模块 — `baabac0`
- **现象**：`python reward/score_wer.py` →
  `ModuleNotFoundError: No module named 'whisper'`。
- **根因**：WER 的英文路径写了 `import whisper`（openai-whisper），但它不在依赖里；而且 openai-whisper 有自己的 torch 版本约束，硬装容易和 dots.tts 的 torch 打架。
- **修复**：改用 **transformers 自带的 ASR pipeline** 加载 `openai/whisper-large-v3`。
  ```python
  from transformers import pipeline
  pipe = pipeline("automatic-speech-recognition", model="openai/whisper-large-v3", device=0, dtype=torch.float16)
  ```
- **为什么这么修**：transformers 是 dots.tts 的**硬依赖（必在）**，复用它**零新增冲突依赖**；且与 seed-tts-eval 同样是 large-v3 后端，**结果可比**。
- **教训**：能复用已装的重依赖（transformers）就别再引入同生态的第二个实现（openai-whisper）。

### B-3 · speechmos 不含 utmos — `1731768`
- **现象**：`python reward/score_utmos.py` →
  `ImportError: cannot import name 'utmos' from 'speechmos'`。
- **根因**：**选错了包**。PyPI 的 `speechmos` 是**微软的 DNSMOS/PLCMOS/AECMOS**，**根本没有 `utmos`** 这个子模块。UTMOS 是另一套东西。
- **修复**：改用社区通用入口 **`torch.hub.load("tarepan/SpeechMOS", "utmos22_strong")`**（UTMOS 的标准轻量实现，自包含、无需 SSL backbone），封装成共享后端 `utmos_backend.py`（`reward/score_utmos.py` 与 `eval/run_utmos.py` 共用，单一事实源），并从 `pyproject` 移除 speechmos。
  ```python
  predictor = torch.hub.load("tarepan/SpeechMOS", "utmos22_strong", trust_repo=True)
  score = predictor(wav_16k.unsqueeze(0), 16000)   # 预测 MOS
  ```
- **为什么这么修**：torch.hub 这条**零额外 pip 依赖**（只用已装的 torch+librosa），且与多数 TTS 论文报告的 UTMOS 同源、可比；做成共享后端避免 reward 与 eval 两处实现漂移。
- **教训**：**名字像 ≠ 是同一个东西**（speechmos 听起来像 MOS 全家桶，实则只有微软那几个）；引依赖前先确认它真有你要的 API。

### B-4 · `select.py` 顶替标准库导致 matplotlib 报错 — sys.path 污染
- **现象**：`python reward/score_sim.py` →
  `ModuleNotFoundError: No module named 'matplotlib'`。但调用链是 `import torch → subprocess → import select`，
  **却加载到 `seed-tts-eval/.../speaker_verification/select.py`**（该文件 `import matplotlib`）。
- **根因（隐蔽）**：原 `score_sim.py` 用 `sys.path.insert(0, sv_dir)` 把 seed-tts-eval 的 SV 目录**插到 sys.path 最前**，
  而该目录有个**通用名文件 `select.py`**，顶替了 Python 标准库的 `select` 模块。torch 启动时 `subprocess` 要 `import select`，
  命中了这个假 select.py → 它又 `import matplotlib` → 环境没装 → 崩。**本质是「通用名文件污染 sys.path 顶部、shadow 标准库」**。
- **修复**：① 在 `score_sim.py` **顶部先 `import torch`**（让标准库 select 先入 `sys.modules` 缓存）；
  ② WavLM 后端改用 **`sys.path.append`（不是 insert(0)）** —— stdlib 路径在前，标准库 select 优先，假 select.py 不再被命中；
  ③ 顺带把默认 SIM 后端换成 **SpeechBrain ECAPA**（见 B-5 决策），彻底绕开 seed-tts-eval 那套老依赖。
- **为什么这么修**：append 而非 insert(0) 是「让第三方目录补充而非抢占」标准库的正确姿势；先 import torch 是双保险。
- **教训**：**给 sys.path 加目录时优先 `append`；`insert(0)` 只在确需覆盖时用**，且要警惕第三方目录里 `select.py`/`models.py`/`utils.py` 这类**通用名**文件 shadow 标准库或他人模块。seed-tts-eval 自己是 `cd` 进该目录跑**子进程**才没事，我们误把它引进主进程。

### B-5 · SIM 改用低摩擦 ECAPA 后端（顺带决策）
- **背景**：seed-tts-eval 的 WavLM-SV 依赖 **`s3prl==0.3.1` + `fire` + 旧 `sklearn` + `torchaudio 0.9`** 等老/重包，还要手动下 Google Drive 的 `wavlm_large_finetune.pth`——冒烟阶段摩擦极大。
- **改进**：`score_sim.py` 加 `--backend`：默认 **`ecapa`（SpeechBrain `spkrec-ecapa-voxceleb`，pip 装、自动下模型、无需 ckpt/s3prl）**；`wavlm`（对榜用）保留为可选。缺 ckpt 时**优雅报错并提示改用 ecapa**，不崩。
- **为什么够用**：我们的 SIM claim 是**比较各 treatment 的差值（delta）**，只要**全程同一个编码器**就内部可比；ECAPA 的绝对值与 Seed-TTS-eval 榜单 WavLM 不可直接横比，但**不影响 RQ1/RQ3 的 treatment 对比**（已在脚本输出里标注）。对榜时再用 `--backend wavlm`。
- **教训**：当"对榜可比性"与"现在能跑出来"冲突时，用**可切换后端**两头兼顾，默认走低摩擦那条。

### B-6 · aggregate_reward 容错缺失打分文件 — 见 §0 #10
- **现象**：`python reward/aggregate_reward.py`（未带 `--w-sim 0`）→ `FileNotFoundError: sim.jsonl`。
- **根因**：无条件读 `sim.jsonl`，但 SIM 这步还没跑（冒烟阶段常先跳过）。
- **修复**：`_index` 文件不存在时返回 `{}`；`main` 检测到缺 `sim/utmos` 文件就把对应权重**置 0 并告警**（WER 仍必需）；终端打印「有效权重」。
- **为什么**：让"先跳过 SIM、只用 WER+UTMOS 冒烟"成为一等支持的路径，而不是靠用户记得加 `--w-sim 0`。
- **教训**：多阶段管线的下游要对**上游产物缺失**鲁棒（尤其可选指标），并把降级**显式告警**而非静默或崩溃。

### B-7 · torchaudio.load 要 torchcodec — 新版 I/O 后端变更
- **现象**：`score_sim.py`（ECAPA 后端）→
  `ImportError: TorchCodec is required for load_with_torchcodec. Please install torchcodec`。
- **根因**：环境里的 **torchaudio 是 2.x 新版**，`torchaudio.load` 已把默认 I/O 后端切到 **torchcodec**；
  而 torchcodec 没装（且它对 FFmpeg/torch 版本很挑，单独装易冲突）。
- **修复**：`score_sim.py` 的 `_load_16k_mono` 改用 **`librosa.load(path, sr=16000, mono=True)`**——
  librosa（已装，score_utmos 也用）走 soundfile，一步完成 加载+重采样+下混，**完全不碰 torchcodec**，
  与 dots.tts 自身音频读取方式一致。
- **顺带**：SpeechBrain 的 `run_opts={"device":"cuda"}` 会报 *Could not parse CUDA device string 'cuda'*（它要 `cuda:N`），
  已改 `"cuda:0"`（原本会 fallback 到 device 0，无害，但消掉告警）。
- **核查**：`grep torchaudio.load` 确认全项目仅 `score_sim` 用过（已修）；其余音频读取都走 librosa/soundfile/dots.tts pipeline，无同类坑。
- **教训**：**音频读取统一走 librosa/soundfile，别用 `torchaudio.load`**——后者的后端在 torchaudio 2.x 变了，会突然要 torchcodec。

### B-8 · DotsTtsModel.from_pretrained 只认本地目录（不自动下 HF）
- **现象**：`python alignment/check_fm_loss.py --ckpt rednote-hilab/dots.tts-base` →
  `FileNotFoundError: Pretrained path /data/.../rednote-hilab/dots.tts-base is missing required files: ['config.json', ...]`。
- **根因**：`DotsTtsModel.from_pretrained()` **把入参当本地目录**，不会 snapshot_download；
  我们传的是 HF repo id，它拼成相对路径找不到。对比：`DotsTtsRuntime.from_pretrained()` 内部先调
  `_resolve_pretrained_path`（本地存在直接用，否则 `snapshot_download`）再加载——**model 这层没有这个解析**。
  这也是为什么候选生成（走 Runtime）能下权重，而对齐训练（直接走 Model）报错。
- **修复**：在 `dots_preprocess.py` 加 `resolve_ckpt()`（复用 dots.tts 自带的 `DotsTtsRuntime._resolve_pretrained_path`）
  + `load_dots_model()` 统一入口；`DotsPreprocessor.from_pretrained` 与 `DpoTrainer`(policy/ref) 全改用它。
- **为什么这么修**：复用 dots.tts 官方解析逻辑，与 Runtime 的加载路径完全一致（本地优先、否则整仓下载到 HF 缓存、去重复用）。
- **教训**：同一个库里 **Runtime 层与 Model 层的 `from_pretrained` 语义可能不同**（前者含 repo-id 解析，后者只认本地路径）——直接用底层 Model 加载时要自己补解析。

### B-9 · 冻结参考模型未搬到 GPU — 设备不一致
- **现象**：`python alignment/train_dots_tts_dpo.py ...` 在 `_ref_forward` →
  `RuntimeError: Input type (torch.cuda.FloatTensor) and weight type (torch.FloatTensor) should be the same`。
- **根因**：`accelerator.prepare(policy, opt, loader)` 只把 **policy** 搬到 GPU；
  冻结的 **ref 模型不参与 DDP、没被 prepare**，仍在 CPU。而 batch 已 `_to_device` 到 cuda → ref 前向时 input(cuda) vs weight(cpu) 不匹配。
  （`check_fm_loss.py` 没暴露是因为它只用一个模型且显式 `pre.model.to(dev)`。）
- **修复**：ref 创建时直接搬设备：`self.ref = load_dots_model(base).eval().requires_grad_(False).to(self.accel.device)`。
- **为什么这么修**：ref 是只读冻结模型，不需要 DDP/optimizer，手动 `.to(device)` 即可；放在 `accel` 建好之后、训练前。
- **教训**：**accelerate 只搬它 `prepare` 的对象**；任何 prepare 之外的模型（冻结 ref、辅助网络）都要自己 `.to(device)`。

### B-10 · 训练只跑一个 epoch 就退出（max_train_steps 失效）
- **现象**：`train_dots_tts_dpo.py`（`max_train_steps: 1500`）在 20 个偏好对上**只跑 20 步就 `✓ DPO 完成`**。
- **根因**：训练循环写成 `for batch in loader:` ——只遍历**一个 epoch**（20 batch）就结束，没有跨 epoch 续训。数据集小于 max_steps 时，`max_train_steps` 形同虚设。
- **修复**：改 `while not done:` 外层循环，反复过 loader，`step` 达到 `max_train_steps` 才停（`train_dots_tts_dpo` 与 `train_open_soar` 同改）。
- **为什么这么修**：DPO/SFT 通常要多 epoch；小数据集更要反复过。这样 `max_train_steps` 真正生效，且与 dots.tts 训练器「按 step 计」的语义一致。
- **教训**：按 `max_train_steps`（而非 epoch）控制训练时，循环必须能**跨 epoch 续喂数据**。
- **顺带**：日志把 `loss` 拆成 `dpo`（纯偏好损失，应↓）与 `sft`（anchor 正则），更易判断 DPO 是否在学。

### B-11 · 训练 checkpoint 存成了 inference 加载不了的格式（**评测前拦截**）
- **现象**：训练能跑、能存，但**评测阶段会加载失败**——因为存的目录缺 `config.json/vocoder.safetensors/speaker_encoder.safetensors/latent_stats.pt`（与 B-8 同类报错）。
- **根因**：trainer 原用 `accelerator.save_state(out_dir)`，那是 **state_dict + optimizer + RNG 的「续训」格式**，**不是** dots.tts `from_pretrained` 要的 HF 风格目录；`DotsTtsRuntime/Model.from_pretrained` 加载不了。
  （这是「训练时没发现、要到评测才炸」的隐藏坑——趁训练空档审查评测链路时提前抓到。）
- **修复**：trainer 改用 dots.tts 自带的 **`model.save_pretrained(out_dir)`**（写 config/llm_config/tokenizer/latent_stats + core/vocoder/speaker_encoder 三套 safetensors）。
  统一封装 `DpoTrainer.save_inference_ckpt`，dpo/open_soar/sft 三个 trainer 共用；先 `accel.unwrap_model`（LoRA 则 `merge_and_unload`）再存；只在 main process 存。
- **顺带**：`save_pretrained` 每次写整模型（~数 GB），故把各 config `save_interval` 调大到只在**末尾存一次**，避免每 500 步刷几十 GB。
- **教训**：**训练存档要存「能被 inference 加载」的格式**，不是只存能续训的 state。跨阶段（训练→评测）的接口要在写代码时就对齐，别等评测才发现。

### B-13 · 代码审查（alignment 核心 reviewer）发现的训练质量/正确性坑
> 6-agent 代码审查里最重要的一批，**影响训练质量**（不崩、但结果次优），都已修：
- **(a) 每步 RNG 不推进 → 噪声多样性塌（MEDIUM，最重要）**：`_fm_per_sample` 在 `fork_rng` 内跑、退出即恢复全局 RNG → 一个 train_step 结束后全局 RNG 不变；DataLoader 只在 epoch 开头推进一次 RNG。结果**同一 epoch 内所有 step 用同一 (x0,t,z) 噪声**，DPO 梯度对单噪声过拟合。修：每步开头 `_advance_global_rng()`（一次 throwaway `torch.rand`）推进全局 RNG → 步间噪声不同；步内 rng_w==rng_l 仍保证 policy/ref/win/lose 四前向共享同一噪声（命门不破）。dpo 与 open_soar 同改。
- **(b) open_soar 扰动没传到说话人分支（MEDIUM，已核对源码）**：`_perturb_waveform` 只改 `sample`，没删 `fbank`/`fbank_lengths` → `xvector_extractor` 见 fbank 存在就用**干净音频**的缓存 fbank 算说话人条件，导致 loser 的 FM 目标(扰动) 与 说话人条件(干净) 不一致。修：扰动时 `pop("fbank")`/`pop("fbank_lengths")`，让 x-vector 从扰动 sample 实时重算；噪声强度改逐样本 std。

- **(d) 杂项**：`_to_device` 不递归（嵌套 `loss_masks` 留 CPU，目前靠 accelerate 的 prepared loader 递归搬运侥幸不崩，已改递归防脱离 accelerate 时炸）；`SftTrainer` 没 override `__init__`、靠 config 写 `mode:sft` 才跳过 ref（已自保证 `self.ref=None`）；`OpenSoarTrainer` 没 override `save`、存档 meta 标成 `"dpo"`（已改 `"open_soar"`）。

### B-15 · DPO 全局 over-optimization：anchor 没锚住声学（**训练崩坏，真问题**）
- **现象**：训练日志看似很好——`reward_acc=1.0`、`reward_margin` 高达 **93–170**（weronly 93–130、multiobj 119–170）、`dpo` 损失≈0。但 **`fm_w`（winner 的 FM 声学损失）从初始 ~1.0 爆到 11–86，`fm_l` 到 160–233**。两个 DPO 臂(dpo_multiobj/dpo_weronly)都这样，open_soar 同理。
- **根因**：DPO 只优化**相对**量 (Δ_w−Δ_l)，发现「把 loser 搞烂」比「把 winner 改好」更易拉开 margin → 把整个 policy 推离预训练分布(全局声学退化)，winner 跟着遭殃。本该由 anchor SFT 拦住，但我的 `anchor_sft_loss` **只正则 ce+eos**——而 **TTS 下 ce=0(文本是条件)、eos≈0.05**，等于 anchor 啥都没约束，winner 的 FM(声学)自由漂移。
- **修复**：**anchor 改成锚住 winner 的 FM 声学损失**(`self.lam_sft * (fm_pol_w.mean() + ce_eos)`)——这才是 TTS 版 DPO+SFT 的正确正则(让 winner 的声学重建保持低)。dpo 与 open_soar 同改。配套调超参防过拟合：`max_train_steps 1500→600`(8ep→3ep)、`beta 0.1→0.2`(收紧漂移)、`lambda_sft 0.1→0.5`（**注：β=0.2/λ_sft=0.5 是中间态，非最终；最终操作点 β=0.5/λ_sft=0.2 见 B-16**）。
- **判断标志**：`fm_w` 应稳定在 ~1 量级、`reward_margin` 个位数到几十(不是 100+)。若 `fm_w` 又爆 = 还需更强 anchor / 更少步 / 更大 β。
- **影响**：第一轮训练(1500 步、弱 anchor)产出的 DPO ckpt **已 over-optimize、生成大概率退化**，需用修复后配置重训 3 个 DPO 臂(sft 不受影响，其 fm 一直 ~0.5 正常)。
- **教训**：① DPO 的"reward_acc=1"具有欺骗性——必须看**绝对**质量量(这里 fm_w)有没有崩，不能只看相对 margin。② SFT anchor 要锚在**真正承载质量的损失项**上(TTS=声学 FM)，不是名义上的 ce/eos。③ 小数据 DPO 极易 over-optimize，**早停+大β+强 anchor** 是必需。这条值得写进论文 §6 稳定性分析 / §7 Limitations。
- **后续**：该修复（`lambda_sft=0.5`、`beta=0.2`）虽治好了过拟合，却引出**反向的「欠拟合」新问题**——anchor 太强把偏好信号一并压死、`reward_margin` 塌到 ~0，并最终诊断出「可达 margin 受 pair 质量差上限制约」的**数据瓶颈**，详见 **B-16**。

### B-16 · DPO anchor 调参的窄稳定窗口：从欠拟合到「数据瓶颈」诊断（调参过程全记录）
> 接 B-15。B-15 把 anchor 从「只锚 ce+eos」改成「锚 winner FM 声学」并收紧超参（`steps 600 / β 0.2 / λ_sft 0.5`），over-optimization 是修好了，但**矫枉过正滑到了欠拟合**。本条记录此后 run1→run2→run3 三次调参的完整弧线，以及它如何把问题从「超参没调好」收敛到「**数据质量差是 margin 的硬上限**」。**当前状态：诊断中、未关闭**——β=0.5 已保留，但 pair 质量差的统计与重造是**下一步、尚未执行**，本条不是「已修复」。
> 环境：2×H100，**188 个训练 pair**，以下 metrics 全程实跑。三档配置每档实跑一轮观测 metrics 后调整。

- **现象（三次调参的 metrics 弧线）**：
  - **run1（B-15 的修复档：`β=0.2 / λ_sft=0.5 / anchor=fm_pol_w.mean()+ce_eos`）**：过拟合修好了——`fm_w`（winner FM 声学损失）从 B-15 那次的爆值回到 **~0.55（正常量级）**。但**反向欠拟合**：`reward_margin` 塌到 **~0.01**，`dpo` 损失卡死在 **ln2≈0.693**，且 `fm_w≈fm_l`。这是 DPO 完全没在「拉开偏好」的特征。
  - **run2（中间档：`β=0.3 / λ_sft=0.2`）**：`fm_w` 健康（**0.6–1.0**），但 `margin` 仍 **~0.01**、`dpo` 仍 **~0.69**、`fm_w≈fm_l`——**仍欠拟合**。
  - **run3（`β=0.5 / λ_sft=0.2`）**：出现**间歇性分离**——多数 step 仍平（`margin~0.01`），但**部分 step 炸开真 margin**：
    - `step593`：`margin=0.778`，`fm_l=1.45` vs `fm_w=0.75`（loser 被推高、winner 压住）；
    - `step598`：`margin=0.478`，`fm_l=1.12` vs `fm_w=0.62`。
    平均 margin 仍低，但这些「炸开」的 step 第一次让我们看清了瓶颈所在。
- **根因（窄稳定窗口 + 真瓶颈）**：anchor 强度（`λ_sft`）存在一个**很窄的稳定窗口**，两侧各有一种退化：
  - **anchor 太弱（`λ_sft=0.1`，即 B-15 的 run0）→ 退化式全局 over-optimization**：模型靠「搞烂 loser（并连累 winner）」廉价拉大 margin → FM 爆、生成崩；`reward_acc=1.0` 是**欺骗性**的（已在 B-15 记录）。
  - **anchor 太强（`λ_sft=0.5`，run1）→ 偏好信号被压死**：`λ=0.5` 的 anchor 把 `fm_w` 死死按在监督最优点；又因为 winner/loser 是**同一句 prompt 的候选、声学高度相似**，按住 `fm_w` 会**连带把 `fm_l` 一起按住** → margin 涨不起来 → DPO 退化成「只在 winner 上做 SFT」。`dpo=ln2` 正是「两臂等价、偏好概率=0.5」的退化签名。
  - **即便落在平衡中点（`λ_sft=0.2`，`β=0.3–0.5`，run2/run3）**：`fm_w` 健康、anchor 没破，但平均 `margin` 仍 ~0.01。run3 的间歇分离揭示真因——**188 个 pair 里大多数是「近似平局」**（同 prompt 的候选声学太像，FM-loss 作隐式奖励时几乎无差），β=0.5 只能把**少数「真有声学质量差」的 pair** 分开（`fm_l` 升、`fm_w` 守在 ~1、anchor 没破），其余被平均掉。**可达 margin 因此受「pair 质量差」这个数据上限制约，不是超参问题。**
- **修复尝试与当前结论（诊断中、未关闭）**：
  - **保留 `β=0.5`**：它是三档里唯一能把「真有质量差的 pair」分开、且不破 anchor（`fm_w` 守在 ~1）的配置。`λ_sft=0.2` 为平衡点。三个 config（`dpo_multiobj_fullparam.yaml` / `dpo_weronly.yaml` / `open_soar_selfcorrect.yaml`）当前均为 **`max_train_steps: 600, beta: 0.5, lambda_sft: 0.2`**（已在 repo 核实）。
  - **下一步（尚未执行，诊断中）**：统计 188 个 pair 的**奖励差（reward-gap）分布**；若证实多数为近似平局，则用 **margin 阈值**（只保留 reward-gap 超阈的 pair）或**更大候选池**重造 pair，从数据侧抬高可达 margin 的上限。**此步尚未做，不得记为「已修复 / 已重造 pair」。**
- **教训**：
  1. **anchor 要锚 winner 的 FM 声学损失**（TTS 下 ce≈0、eos≈0.05，名义 ce/eos anchor 等于没锚）——这是 B-15 的结论，B-16 进一步证明它的**强度**也必须落在窄窗口里。
  2. **盯绝对质量量（`fm_w`），别只看相对的 `reward_acc`/`margin`**：`reward_acc=1.0` 曾掩盖一次彻底崩坏（run0）；`margin~0`+`dpo=ln2` 则是另一端的「假装在训」（run1）。两端都要靠绝对量识破。
  3. **可达 margin 受 pair 质量差的上限制约**：用 FM-loss 当隐式奖励，只能分开「真不一样」的 pair → **pair 构造（margin 阈值 / 更大候选池）与 loss/β 同等重要**，甚至是更靠前的瓶颈。
  4. **窄稳定窗口本身是个发现**：`λ_sft` 太弱→全局过拟合（搞烂 loser 连累 winner、FM 爆），太强→偏好被压死（退化成 SFT），中点也只在「真有质量差的 pair」上才分得开。这条与 B-15 一起，构成论文 §6 稳定性分析 / §7 Limitations 的完整证据链（over-optimization ↔ under-fitting ↔ data-bottleneck 三态）。

### B-17 · FM 损失探针：发现 L_FM 与 reward 反相关（ρ=−0.5，DPO-FM 隐式奖励错配）
> 本条是**指针/摘要**，完整推导、逐对数据、机理与对论文的影响见 **`docs/06-核心发现-FM损失与奖励错配.md`**（本条不重复其全文）。它把 B-15/B-16 那条「调不动」的调参史从「超参/数据问题」上推到了**方法根因**。

- **被检验的猜想**：DPO-FM 把 flow-matching 训练损失 `L_FM` 当隐式 log-likelihood 代理（Diffusion-DPO 的连续-latent 改编，见 `docs/01` §2）。其**前提**是 `L_FM` 必须跟 perceptual reward 同向——被偏好（高 WER/SIM/UTMOS）的候选应有**更低**的 `L_FM`。训练里 `reward_margin` 长期 ~0.01（B-16），提出三假设：H1 噪声（单次 (x0,t) 方差太大，MC 平均可修）／ H2 无信息 ／ **H3 反相关**（被偏好候选 `L_FM` 反而更高，根本性错配）。
- **决定性探针**：`alignment/probe_fm_reward.py`——取 **N=24** 个 best_worst pair，每对 **K=24** 次 MC（不同 (x0,t)），每 draw 内 win/lose **共享同一 (x0,t)**、`no_grad`；度量「去噪 FM margin = `L_FM^lose − L_FM^win`」（>0 ⇒ winner 更优）及其与 reward 差的相关。复现：
  ```
  python alignment/probe_fm_reward.py --pairs pairs/out/pairs_best_worst.jsonl --n 24 --k 24
  ```
- **结果（决定性，证实 H3、证伪 H1）**：
  - 去噪 FM margin 为正的 pair 仅 **4/24 (17%)**；均值 **−0.0215**（winner 平均 `L_FM` 反而更高）。
  - 平均 **win_rate = 0.33**（winner 被偏好概率低于抛硬币 0.5）。
  - **Pearson(FM margin, reward 差) = −0.496**；Spearman = −0.302（reward 差越大 → FM margin 越负）。
  - 单次 margin 标准差 **0.0979 ≫ |MC 均值| 0.0215** → 单步信号确实高噪，但**去噪后真信号是负的** → **非噪声问题（H1 否），是错配（H3）**。
  - 逐对佐证：`[4]` reward_gap=+2.839 → MC=−0.1604（最好的 winner，FM 最嫌弃）；`[23]` gap=+2.758 → win_rate=0.08；`[1]` gap=+2.698 → MC=−0.0804。少数正例如 `[5]` gap=+2.765 MC=+0.0268 属趋势内噪声。
- **机理（猜想）**：`L_FM` 衡量「模型 flow 头下的 typicality/似然」，不是 perceptual 质量；perceptually 更优的候选（更清晰、更自然）往往在模型自然分布上**更不典型** → `L_FM` 反而更高。于是 reward 最高的候选恰是似然最低的（经典 likelihood-vs-quality 错配，此处首次在连续-latent TTS 上量化到 ρ≈−0.5）。**注：此错配非由生成设置中介**——`inspect_guidance_confound` 已排除 guidance 驱动（reward 与 guidance/num_steps/speaker_scale 的 |Pearson|≤0.12），故为 FM 内在性质。
- **结论指向**：这解释了 **B-15（弱 anchor 过拟合）↔ B-16（强 anchor 欠拟合 margin→0）** 同一病根——DPO 想压低 winner 的 `L_FM`，但 winner 天生 `L_FM` 高，目标与模型似然几何对着干 → 学不动。对各臂的影响：`open_soar`（reward-free、偏好在「轨迹洁净度」）与 `sft`（仅在 winners 上做监督 FM，不做 win/lose 的 `L_FM` 对比）**不踩此坑**，可能才是真正起作用的建设性臂。
- **guidance-confound：已排除（原 open question 已关闭）**：用 `candidates/inspect_guidance_confound.py`（纯元数据 join，188 对、0 失败）实测 winner/loser 的生成设置**统计无系统差异**——guidance_scale 1.114 vs 1.093、num_steps 11.85 vs 10.44、speaker_scale 1.371 vs 1.339，三者与 reward 差均仅 **|Pearson|≤0.12**。→ 反相关**不是候选生成混淆，是 FM 内在性质（intrinsic misspecification）**。
- **统计严谨（n=24 pilot）**：核心方向稳健——4/24 为正的二项检验 **p<0.001**、Pearson −0.496 在 n=24 显著（临界 |r|≈0.40）；但 **Spearman −0.302 偏弱、该 n 不显著（p≈0.15）**，相关性精确量级正由全量 **N=188** 复测收紧（方向已定）。
- **影响（强假设、非终稿）**：贡献可能从「一个能用的 DPO 配方」转为**机理性警示研究**——把 DPO/Diffusion-DPO 直接搬到连续-latent TTS（FM-loss 当隐式奖励）是错配的，不可照搬离散-token 偏好配方。详见 `docs/06`。

### C-2 · Whisper 推理期的两类提示 → 消音 — `646dbc7`
1. `A custom logits processor of type SuppressTokens... will take precedence`（两条）
   - **是什么**：传 `language/task` 时 pipeline 会建「抑制特殊 token」处理器，模型 `generation_config` 里**也**预置了同类；transformers 提示「用你传的这个」。**纯播报，行为正确**。
2. `Ignoring clean_up_tokenization_spaces=True for BPE tokenizer ... destructive`
   - **是什么**：Whisper 的 BPE tokenizer 解码后默认清理空格，对 BPE 有破坏性（删标点前空格）。**对我们零影响**——`score_wer.py` 算 WER 前已 `_normalize`（小写+删全部标点+合并空白），这点差异早被洗掉。
- **修复**：把 transformers 日志压到 error 级（只屏蔽 warning/info，真正 error 仍显示）：
  ```python
  os.environ.setdefault("TRANSFORMERS_VERBOSITY", "error")
  from transformers.utils import logging as hf_logging; hf_logging.set_verbosity_error()
  os.environ.setdefault("TOKENIZERS_PARALLELISM", "false")
  ```
- **教训**：**良性 warning 可以消音，但不要为消音去改会动结果的参数**（例如别真去设 `fix_mistral_regex=True`，见 C-3）。

### C-6 · `unauthenticated requests to the HF Hub` 提示（良性）
- **现象**：下载 SpeechBrain ECAPA / dots.tts 权重时打印 `Warning: You are sending unauthenticated requests to the HF Hub. Please set a HF_TOKEN ...`。
- **是什么**：huggingface_hub 提示「未登录，受匿名速率限制」。下载**照常成功**，只是慢一点/有速率上限。
- **处理**：不用管；若下载大模型频繁限速，可 `export HF_TOKEN=...`（HF 账号 token）提速。**不影响结果**。

### C-5 · 保存 checkpoint 时的 `Removed shared tensor` 提示（良性）
- **现象**：`accelerator.save_state` 打印
  `[RANK 0] Removed shared tensor {...vocoder...lstm..., core.llm.lm_head.weight} while saving. This should be OK...`。
- **是什么**：safetensors 保存时检测到**权重共享/绑定**——`core.llm.lm_head.weight` 与词嵌入 tied、vocoder 的 LSTM 权重内部共享存储；它把重复的去掉只存一份。**它自己也说 "This should be OK"**，reload 时会自动重建。
- **处理**：**不用动**。属正常的 tied-weights 行为。
- **教训**：tied weights（lm_head↔embedding）在保存时被 safetensors 去重是常态，不是数据丢失。

### C-4 · 模型加载期的良性 warning 已统一静音（`common.py`）
跑 `check_fm_loss.py` / 训练 / 推理时，加载 dots.tts 模型会打印若干良性 warning。已在 `common.py` 顶部统一处理（每个脚本都 import 它）：
1. `model of type dots_tts to instantiate ''`（transformers 注册噪声）→ `TRANSFORMERS_VERBOSITY=error` 压掉。
2. `tokenizer ... fix_mistral_regex=True`（见 C-3，**绝不能真改**）→ 同上压掉。
3. `weight_norm is deprecated`（**dots.tts 的 BigVGAN vocoder** 用了旧 torch API，与我们无关）→ `warnings.filterwarnings` 针对性忽略。
4. `Download complete: 0.00B`（huggingface_hub 对已缓存文件的进度条）→ **保留不压**（避免连真实大文件下载进度一起隐藏）。
- 全用 `setdefault`/针对性过滤，用户可覆盖（`export TRANSFORMERS_VERBOSITY=warning` 看全部）。
- **教训**：良性 warning 统一在共享模块（`common.py`）静音，比每个脚本各写一遍干净；但**只压不影响结果的，且保留真实下载进度**。

### C-3 · 模型加载期的两条提示（**保持原样，勿改**）
跑候选生成 / 自检时，dots.tts 加载会打印：
1. `You are using a model of type dots_tts to instantiate a model of type ''`
   - dots.tts 自定义架构在 transformers 注册的样板噪声，**无影响**。
2. `tokenizer ... incorrect regex pattern ... set fix_mistral_regex=True`
   - **是什么**：transformers 觉得 dots.tts 的 tokenizer 正则不符合 Mistral「标准」。
   - **为什么不能改**：dots.tts 就是用这个 tokenizer **原样训练**的；我们用 `model.tokenizer`（同一个）给候选/训练文本分词 → **与模型训练时一致才是对的**。设 `fix_mistral_regex=True` 反而会让分词偏离模型预期、**损坏结果**。
- **教训**：**「修复某 warning」不等于「让结果更对」**——有时按 warning 建议改反而是错的。判断标准永远是「是否与模型训练时一致」。

### D-1 · 数据适配器对齐 dots.tts 真实产物 — `5f46911`

### D-2 · 实现 `dots_preprocess.py` 接缝 + 共享-RNG + 自检 — `4851f41`

### D-3 · `patch_size=4` 的意外验证（无需改代码）
- **背景**：早期代码探查以为 dots.tts `patch_size=8`；但服务器加载日志显示真实值是 **`patch_size=4`**（`sample_rate=48000 patch_size=4`）。

- **背景**：候选生成是最贵的一步（~3h/188prompt）；原实现只在**全部跑完**才写 `candidates_index.jsonl`，中途中断 = 整个 3h 白跑、重跑从头来。

## E. 通用经验总结（给后来者）

1. **设计期只能语法检查，运行期错误必然在 GPU 机器上才暴露**——所以「本机 `py_compile` 通过」≠「服务器能跑」。早跑小样冒烟（`--limit`）尽快触发真问题。
2. **外部依赖的「名字、版本、API」三者都要核实**：speechmos 名字像 UTMOS 全家桶其实没有 utmos（B-3）、版本臆测 `>=1.0.0` 不存在（A-2）。
3. **优先复用已装的重依赖**：WER 用 transformers（已装）而非 openai-whisper（B-1）；UTMOS 用 torch.hub 而非再引包（B-3）。
4. **契约值从模型派生、绝不硬编码**：`patch_size` 真值与假设不符时代码自动适配（D-3）。
5. **warning 分两种**：性能/弃用类（如 sequential-on-GPU、torch_dtype）值得真改（C-1）；行为播报类（SuppressTokens、BPE 清空格）消音即可，且**有的按建议改反而错**（C-3 的 fix_mistral_regex）。判断基准永远是「**是否与模型训练时一致**」。
6. **接缝要有自检**：`check_fm_loss.py` 把「方法能否成立」的命门（共享-RNG 决定论）做成可一键验证的 PASS/FAIL，开训前必跑。
