## A. 环境与依赖类错误

### A-1 · setuptools 扁平布局打包失败 — `74f01de`
- **现象**：`bash env/setup_env.sh` 的 `[3/6] pip install -e .` 报
  `error: Multiple top-level packages discovered in a flat-layout: ['eval','data','pairs',...]`。
- **根因**：本项目用 `sys.path.insert` + `from common import ...` 的脚本组织，**不是一个可安装的 Python 包**；但 setuptools 看到一堆顶层目录（`eval/` `data/` …），以为要把它们都当包打进去，自动发现失败。
- **修复**：在 `pyproject.toml` 显式声明「无包、无模块」，关闭自动发现：
  ```toml
  [tool.setuptools]
  packages = []
  py-modules = []
  ```
  顺带把弃用的 `license = {text=...}` 改成 SPDX 字符串 `license = "Apache-2.0"`。
- **为什么这么修**：我们 `pip install -e .` 的**唯一目的是装增量依赖**（jiwer/peft/…），不需要把项目本身当包导入；声明空包是最干净、最不易误伤的做法（比 `src-layout` 重构成本低）。
- **教训**：扁平多目录 + 想用 `pip install -e .` 只装依赖时，**必须显式声明 packages/py-modules**，否则 setuptools 自动发现会炸。

### A-4 · `+` 不是 bash 的命令连接符（操作小坑）

### B-4 · `select.py` 顶替标准库导致 matplotlib 报错 — sys.path 污染
- **现象**：`python reward/score_sim.py` →
  `ModuleNotFoundError: No module named 'matplotlib'`。但调用链是 `import torch → subprocess → import select`，
  **却加载到 `seed-tts-eval/.../speaker_verification/select.py`**（该文件 `import matplotlib`）。
- **根因（隐蔽）**：原 `score_sim.py` 用 `sys.path.insert(0, sv_dir)` 把 seed-tts-eval 的 SV 目录**插到 sys.path 最前**，
  而该目录有个**通用名文件 `select.py`**，顶替了 Python 标准库的 `select` 模块。torch 启动时 `subprocess` 要 `import select`，
  命中了这个假 select.py → 它又 `import matplotlib` → 环境没装 → 崩。**本质是「通用名文件污染 sys.path 顶部、shadow 标准库」**。
- **修复**：① 在 `score_sim.py` **顶部先 `import torch`**（让标准库 select 先入 `sys.modules` 缓存）；
  ② WavLM 后端改用 **`sys.path.append`（不是 insert(0)）** —— stdlib 路径在前，标准库 select 优先，假 select.py 不再被命中；
  ③ 顺带把默认 SIM 后端换成 **SpeechBrain ECAPA**（见 B-5 决策），彻底绕开 seed-tts-eval 那套老依赖。
- **为什么这么修**：append 而非 insert(0) 是「让第三方目录补充而非抢占」标准库的正确姿势；先 import torch 是双保险。
- **教训**：**给 sys.path 加目录时优先 `append`；`insert(0)` 只在确需覆盖时用**，且要警惕第三方目录里 `select.py`/`models.py`/`utils.py` 这类**通用名**文件 shadow 标准库或他人模块。seed-tts-eval 自己是 `cd` 进该目录跑**子进程**才没事，我们误把它引进主进程。

### B-5 · SIM 改用低摩擦 ECAPA 后端（顺带决策）
- **背景**：seed-tts-eval 的 WavLM-SV 依赖 **`s3prl==0.3.1` + `fire` + 旧 `sklearn` + `torchaudio 0.9`** 等老/重包，还要手动下 Google Drive 的 `wavlm_large_finetune.pth`——冒烟阶段摩擦极大。

- **教训**：当"对榜可比性"与"现在能跑出来"冲突时，用**可切换后端**两头兼顾，默认走低摩擦那条。

### B-8 · DotsTtsModel.from_pretrained 只认本地目录（不自动下 HF）

### B-9 · 冻结参考模型未搬到 GPU — 设备不一致
- **现象**：`python alignment/train_dots_tts_dpo.py ...` 在 `_ref_forward` →
  `RuntimeError: Input type (torch.cuda.FloatTensor) and weight type (torch.FloatTensor) should be the same`。
- **根因**：`accelerator.prepare(policy, opt, loader)` 只把 **policy** 搬到 GPU；
  冻结的 **ref 模型不参与 DDP、没被 prepare**，仍在 CPU。而 batch 已 `_to_device` 到 cuda → ref 前向时 input(cuda) vs weight(cpu) 不匹配。
  （`check_fm_loss.py` 没暴露是因为它只用一个模型且显式 `pre.model.to(dev)`。）
- **修复**：ref 创建时直接搬设备：`self.ref = load_dots_model(base).eval().requires_grad_(False).to(self.accel.device)`。
- **为什么这么修**：ref 是只读冻结模型，不需要 DDP/optimizer，手动 `.to(device)` 即可；放在 `accel` 建好之后、训练前。
- **教训**：**accelerate 只搬它 `prepare` 的对象**；任何 prepare 之外的模型（冻结 ref、辅助网络）都要自己 `.to(device)`。

### B-10 · 训练只跑一个 epoch 就退出（max_train_steps 失效）
- **现象**：`train_dots_tts_dpo.py`（`max_train_steps: 1500`）在 20 个偏好对上**只跑 20 步就 `✓ DPO 完成`**。
- **根因**：训练循环写成 `for batch in loader:` ——只遍历**一个 epoch**（20 batch）就结束，没有跨 epoch 续训。数据集小于 max_steps 时，`max_train_steps` 形同虚设。
- **修复**：改 `while not done:` 外层循环，反复过 loader，`step` 达到 `max_train_steps` 才停（`train_dots_tts_dpo` 与 `train_open_soar` 同改）。
- **为什么这么修**：DPO/SFT 通常要多 epoch；小数据集更要反复过。这样 `max_train_steps` 真正生效，且与 dots.tts 训练器「按 step 计」的语义一致。
- **教训**：按 `max_train_steps`（而非 epoch）控制训练时，循环必须能**跨 epoch 续喂数据**。
- **顺带**：日志把 `loss` 拆成 `dpo`（纯偏好损失，应↓）与 `sft`（anchor 正则），更易判断 DPO 是否在学。

### B-11 · 训练 checkpoint 存成了 inference 加载不了的格式（**评测前拦截**）

### B-13 · 代码审查（alignment 核心 reviewer）发现的训练质量/正确性坑
> 6-agent 代码审查里最重要的一批，**影响训练质量**（不崩、但结果次优），都已修：
- **(a) 每步 RNG 不推进 → 噪声多样性塌（MEDIUM，最重要）**：`_fm_per_sample` 在 `fork_rng` 内跑、退出即恢复全局 RNG → 一个 train_step 结束后全局 RNG 不变；DataLoader 只在 epoch 开头推进一次 RNG。结果**同一 epoch 内所有 step 用同一 (x0,t,z) 噪声**，DPO 梯度对单噪声过拟合。修：每步开头 `_advance_global_rng()`（一次 throwaway `torch.rand`）推进全局 RNG → 步间噪声不同；步内 rng_w==rng_l 仍保证 policy/ref/win/lose 四前向共享同一噪声（命门不破）。dpo 与 open_soar 同改。
- **(b) open_soar 扰动没传到说话人分支（MEDIUM，已核对源码）**：`_perturb_waveform` 只改 `sample`，没删 `fbank`/`fbank_lengths` → `xvector_extractor` 见 fbank 存在就用**干净音频**的缓存 fbank 算说话人条件，导致 loser 的 FM 目标(扰动) 与 说话人条件(干净) 不一致。修：扰动时 `pop("fbank")`/`pop("fbank_lengths")`，让 x-vector 从扰动 sample 实时重算；噪声强度改逐样本 std。

### B-15 · DPO 全局 over-optimization：anchor 没锚住声学（**训练崩坏，真问题**）
- **现象**：训练日志看似很好——`reward_acc=1.0`、`reward_margin` 高达 **93–170**（weronly 93–130、multiobj 119–170）、`dpo` 损失≈0。但 **`fm_w`（winner 的 FM 声学损失）从初始 ~1.0 爆到 11–86，`fm_l` 到 160–233**。两个 DPO 臂(dpo_multiobj/dpo_weronly)都这样，open_soar 同理。
- **根因**：DPO 只优化**相对**量 (Δ_w−Δ_l)，发现「把 loser 搞烂」比「把 winner 改好」更易拉开 margin → 把整个 policy 推离预训练分布(全局声学退化)，winner 跟着遭殃。本该由 anchor SFT 拦住，但我的 `anchor_sft_loss` **只正则 ce+eos**——而 **TTS 下 ce=0(文本是条件)、eos≈0.05**，等于 anchor 啥都没约束，winner 的 FM(声学)自由漂移。
- **修复**：**anchor 改成锚住 winner 的 FM 声学损失**(`self.lam_sft * (fm_pol_w.mean() + ce_eos)`)——这才是 TTS 版 DPO+SFT 的正确正则(让 winner 的声学重建保持低)。dpo 与 open_soar 同改。配套调超参防过拟合：`max_train_steps 1500→600`(8ep→3ep)、`beta 0.1→0.2`(收紧漂移)、`lambda_sft 0.1→0.5`（**注：β=0.2/λ_sft=0.5 是中间态，非最终；最终操作点 β=0.5/λ_sft=0.2 见 B-16**）。
- **判断标志**：`fm_w` 应稳定在 ~1 量级、`reward_margin` 个位数到几十(不是 100+)。若 `fm_w` 又爆 = 还需更强 anchor / 更少步 / 更大 β。
- **影响**：第一轮训练(1500 步、弱 anchor)产出的 DPO ckpt **已 over-optimize、生成大概率退化**，需用修复后配置重训 3 个 DPO 臂(sft 不受影响，其 fm 一直 ~0.5 正常)。
- **教训**：① DPO 的"reward_acc=1"具有欺骗性——必须看**绝对**质量量(这里 fm_w)有没有崩，不能只看相对 margin。② SFT anchor 要锚在**真正承载质量的损失项**上(TTS=声学 FM)，不是名义上的 ce/eos。③ 小数据 DPO 极易 over-optimize，**早停+大β+强 anchor** 是必需。这条值得写进论文 §6 稳定性分析 / §7 Limitations。
- **后续**：该修复（`lambda_sft=0.5`、`beta=0.2`）虽治好了过拟合，却引出**反向的「欠拟合」新问题**——anchor 太强把偏好信号一并压死、`reward_margin` 塌到 ~0，并最终诊断出「可达 margin 受 pair 质量差上限制约」的**数据瓶颈**，详见 **B-16**。

### B-16 · DPO anchor 调参的窄稳定窗口：从欠拟合到「数据瓶颈」诊断（调参过程全记录）
> 接 B-15。B-15 把 anchor 从「只锚 ce+eos」改成「锚 winner FM 声学」并收紧超参（`steps 600 / β 0.2 / λ_sft 0.5`），over-optimization 是修好了，但**矫枉过正滑到了欠拟合**。本条记录此后 run1→run2→run3 三次调参的完整弧线，以及它如何把问题从「超参没调好」收敛到「**数据质量差是 margin 的硬上限**」。**当前状态：诊断中、未关闭**——β=0.5 已保留，但 pair 质量差的统计与重造是**下一步、尚未执行**，本条不是「已修复」。
> 环境：2×H100，**188 个训练 pair**，以下 metrics 全程实跑。三档配置每档实跑一轮观测 metrics 后调整。

- **现象（三次调参的 metrics 弧线）**：
  - **run1（B-15 的修复档：`β=0.2 / λ_sft=0.5 / anchor=fm_pol_w.mean()+ce_eos`）**：过拟合修好了——`fm_w`（winner FM 声学损失）从 B-15 那次的爆值回到 **~0.55（正常量级）**。但**反向欠拟合**：`reward_margin` 塌到 **~0.01**，`dpo` 损失卡死在 **ln2≈0.693**，且 `fm_w≈fm_l`。这是 DPO 完全没在「拉开偏好」的特征。
  - **run2（中间档：`β=0.3 / λ_sft=0.2`）**：`fm_w` 健康（**0.6–1.0**），但 `margin` 仍 **~0.01**、`dpo` 仍 **~0.69**、`fm_w≈fm_l`——**仍欠拟合**。
  - **run3（`β=0.5 / λ_sft=0.2`）**：出现**间歇性分离**——多数 step 仍平（`margin~0.01`），但**部分 step 炸开真 margin**：
    - `step593`：`margin=0.778`，`fm_l=1.45` vs `fm_w=0.75`（loser 被推高、winner 压住）；
    - `step598`：`margin=0.478`，`fm_l=1.12` vs `fm_w=0.62`。
    平均 margin 仍低，但这些「炸开」的 step 第一次让我们看清了瓶颈所在。
- **根因（窄稳定窗口 + 真瓶颈）**：anchor 强度（`λ_sft`）存在一个**很窄的稳定窗口**，两侧各有一种退化：
  - **anchor 太弱（`λ_sft=0.1`，即 B-15 的 run0）→ 退化式全局 over-optimization**：模型靠「搞烂 loser（并连累 winner）」廉价拉大 margin → FM 爆、生成崩；`reward_acc=1.0` 是**欺骗性**的（已在 B-15 记录）。
  - **anchor 太强（`λ_sft=0.5`，run1）→ 偏好信号被压死**：`λ=0.5` 的 anchor 把 `fm_w` 死死按在监督最优点；又因为 winner/loser 是**同一句 prompt 的候选、声学高度相似**，按住 `fm_w` 会**连带把 `fm_l` 一起按住** → margin 涨不起来 → DPO 退化成「只在 winner 上做 SFT」。`dpo=ln2` 正是「两臂等价、偏好概率=0.5」的退化签名。
  - **即便落在平衡中点（`λ_sft=0.2`，`β=0.3–0.5`，run2/run3）**：`fm_w` 健康、anchor 没破，但平均 `margin` 仍 ~0.01。run3 的间歇分离揭示真因——**188 个 pair 里大多数是「近似平局」**（同 prompt 的候选声学太像，FM-loss 作隐式奖励时几乎无差），β=0.5 只能把**少数「真有声学质量差」的 pair** 分开（`fm_l` 升、`fm_w` 守在 ~1、anchor 没破），其余被平均掉。**可达 margin 因此受「pair 质量差」这个数据上限制约，不是超参问题。**
- **修复尝试与当前结论（诊断中、未关闭）**：
  - **保留 `β=0.5`**：它是三档里唯一能把「真有质量差的 pair」分开、且不破 anchor（`fm_w` 守在 ~1）的配置。`λ_sft=0.2` 为平衡点。三个 config（`dpo_multiobj_fullparam.yaml` / `dpo_weronly.yaml` / `open_soar_selfcorrect.yaml`）当前均为 **`max_train_steps: 600, beta: 0.5, lambda_sft: 0.2`**（已在 repo 核实）。
  - **下一步（尚未执行，诊断中）**：统计 188 个 pair 的**奖励差（reward-gap）分布**；若证实多数为近似平局，则用 **margin 阈值**（只保留 reward-gap 超阈的 pair）或**更大候选池**重造 pair，从数据侧抬高可达 margin 的上限。**此步尚未做，不得记为「已修复 / 已重造 pair」。**
- **教训**：
  1. **anchor 要锚 winner 的 FM 声学损失**（TTS 下 ce≈0、eos≈0.05，名义 ce/eos anchor 等于没锚）——这是 B-15 的结论，B-16 进一步证明它的**强度**也必须落在窄窗口里。
  2. **盯绝对质量量（`fm_w`），别只看相对的 `reward_acc`/`margin`**：`reward_acc=1.0` 曾掩盖一次彻底崩坏（run0）；`margin~0`+`dpo=ln2` 则是另一端的「假装在训」（run1）。两端都要靠绝对量识破。
  3. **可达 margin 受 pair 质量差的上限制约**：用 FM-loss 当隐式奖励，只能分开「真不一样」的 pair → **pair 构造（margin 阈值 / 更大候选池）与 loss/β 同等重要**，甚至是更靠前的瓶颈。
  4. **窄稳定窗口本身是个发现**：`λ_sft` 太弱→全局过拟合（搞烂 loser 连累 winner、FM 爆），太强→偏好被压死（退化成 SFT），中点也只在「真有质量差的 pair」上才分得开。这条与 B-15 一起，构成论文 §6 稳定性分析 / §7 Limitations 的完整证据链（over-optimization ↔ under-fitting ↔ data-bottleneck 三态）。

### B-17 · FM 损失探针：automatic-metric reward 偏好与模型 flow 似然反相关（稳健 Spearman −0.187，N=188，preference-likelihood 对齐失败）
> 本条是**指针/摘要**，完整推导、逐对数据、机理与对论文的影响见 **`docs/06-核心发现-FM损失与奖励错配.md`**（本条不重复其全文）。它把 B-15/B-16 那条「调不动」的调参史从「超参/数据问题」上推到**方法层根因**：**不是** `L_FM` 当似然代理本身失效（它有效——open_soar 用同一 `L_FM` 学得满分），**而是** automatic-metric reward 偏好与模型 flow 似然反向（**preference-likelihood 对齐失败**）。

- **被检验的猜想**：DPO-FM 把 flow-matching 训练损失 `L_FM` 当隐式 log-likelihood 代理（Diffusion-DPO 的连续-latent 改编，见 `docs/01` §2）。其**前提**是 `L_FM` 必须跟 automatic-metric reward 同向——被偏好（高 WER/SIM/UTMOS 聚合 reward）的候选应有**更低**的 `L_FM`。训练里 `reward_margin` 长期 ~0.01（B-16），提出三假设：H1 噪声（单次 (x0,t) 方差太大，MC 平均可修）／ H2 无信息 ／ **H3 反相关**（被偏好候选 `L_FM` 反而更高，根本性错配）。
- **决定性探针**：`alignment/probe_fm_reward.py`——取 best_worst pair，每对 K 次 MC（不同 (x0,t)），每 draw 内 win/lose **共享同一 (x0,t)**、`no_grad`；度量「去噪 FM margin = `L_FM^lose − L_FM^win`」（>0 ⇒ winner 更优）及其与 reward 差的相关。**全量 N=188（K=16）为主数字**，n=24 仅作早期 pilot。复现：
  ```
  python alignment/probe_fm_reward.py --pairs pairs/out/pairs_best_worst.jsonl --n 188 --k 16
  ```
- **结果（全量 N=188，主数字）**：
  - **头条（稳健量优先）**：去噪 FM margin 与 automatic-metric reward 差 **Spearman ρ=−0.187（p≈0.01、ρ²≈3.5%，按 Cohen 属弱单调反相关）**——这是该领的稳健头条；**Pearson −0.411（p≈1e-8）并列标注为「杠杆放大的线性系数」**（约 2.2× 于 Spearman，由少数高 reward-gap 点撑起）。N=188 临界 |r|≈0.143，两者均过线、方向一致（reward 差越大 → FM 越不偏好 winner）。
  - 去噪 FM margin 为正的 pair **82/188 (44%)**；均值 **−0.0071**（≈0）；平均 **win_rate = 0.47**。binomial 82/188 vs 0.5 **p=0.093——略低于 0.5 但不显著**。故「平均无系统偏好」大半是 near-tie 数据产物、**不作独立证据**，核心只靠上面的反相关（且须在高-gap 非平局子集上证明存活）。
  - 单次 margin 标准差 **0.0892** ≫ |MC 均值| 0.0071 → 单步信号高噪、去噪后均值≈0。
- **与 n=24 pilot 对比 + 诚实修正（自我修正叙事）**：早期 n=24 pilot 表观更强——4/24 (17%) 为正、win_rate **0.33**、Pearson **−0.496**、Spearman **−0.302**。全量 N=188 修正：win_rate 0.33→**0.47**、为正占比 17%→**44%**。故 n=24 那个「winner **系统性** FM 更差」是**小样本 / 高杠杆点造成的高估**，被全量证伪；但**反相关稳健且更显著**——Pearson 收紧到 p≈1e-8、Spearman 从 n=24 时不显著（p≈0.15）变为 N=188 显著（p≈0.01）。**头条数字改用稳健的 Spearman ρ=−0.187（ρ²≈3.5%、弱单调；Pearson −0.411 为杠杆放大的线性系数）**，不再用「win_rate 0.33 / 4-of-24 / winner 系统性更差」这类被全量证伪的表述（n=24 仅作 pilot 提及）。
- **机理（likelihood-vs-quality / CFG off-manifold gap）**：`L_FM` 衡量「模型 flow 头下的 typicality/似然」，不是 automatic-metric 质量。best-vs-worst 在质量奖励上选出的 winner，往往是该 pair 里**更不典型(off-manifold)**的成员（**不论由哪个生成 knob 造成**，故**不归因到 guidance 旋钮本身**——winner/loser 的 guidance 统计无差异）→ 模型 flow 似然反而**更低**。于是 reward 越高的 pair、FM 越不偏好 winner——这是教科书级 **likelihood-vs-quality / classifier-free-guidance off-manifold** gap（cf. Theis et al. 2016 似然≠质量；Ho & Salimans 2022 CFG 以似然换保真度；Gao et al. 2023 reward over-optimization）。**贡献定位（去「首次」化）**：据我们所知，这是把该**已知** gap **首批（among the first, to our knowledge）**在连续-latent flow-matching TTS 上做**领域量化**（Spearman −0.187、N=188），而非「首次发现/中心发现」一个新现象。**关键区分**：失败的是 **preference-likelihood 对齐**（automatic-metric 偏好与 flow 似然反向），**不是** `L_FM` 作为似然代理本身——后者**完好**（open_soar 用同一 `L_FM`、似然对齐的偏好训得满分，见下「结论指向」/docs06 §4.2）。一句话：likelihood-based DPO 在 reward 偏好呈 off-manifold 属性时是**错的工具**。
- **结论指向**：这解释了 **B-15（弱 anchor 过拟合）↔ B-16（强 anchor 欠拟合 margin→0）** 同一病根——FM 似然不是 automatic-metric reward 偏好的有效隐式奖励，依据二：(1) 对随机 winner/loser，FM 平均无系统偏好（mean≈0、win_rate 0.47、binomial p=0.093）→ 对应 DPO-FM 的 `margin→0` 欠拟合（大半 near-tie 产物，不作独立证据）；(2) FM margin 与 reward 差**反相关**（稳健 Spearman −0.187）→ 在质量差最大的 pair 上 FM **最不偏好 winner**（指错方向）。DPO 想压低 winner 的 `L_FM`，但偏好方向与模型似然几何对着干 → 学不动。**两层须分清**：likelihood-surrogate 有效性（完好）vs preference-likelihood 对齐（真失败）。对各臂的影响：`open_soar`（reward-free、偏好在「轨迹洁净度」、与似然同向）与 `sft`（仅在 winners 上做监督 FM，不做 win/lose 的 `L_FM` 对比）**不踩此坑**——它们是不依赖「`L_FM` 当 logprob 且偏好须顺似然」的建设性臂；注 open_soar 的 live-training「学满分」是 **by construction**（loser 是加噪 rollout、margin 巨大、近定义性），真正证据是 held-out 音质（Table 1，planned）。
- **guidance-confound 已由 `probe_analysis.py` 裁决：intrinsic 确立（偏相关存活，partial r=−0.392）**：`alignment/probe_analysis.py` 先**修正了第一轮审稿（`docs/07` C1/C5/DA）指出的「confound 测错量」问题**——旧 `candidates/inspect_guidance_confound.py` 测的是 corr(reward-gap, setting-gap)（guidance/num_steps/speaker 三组生成设置 winner/loser 统计无系统差异、与 reward 差仅 +0.108/+0.118/+0.108、均预测方向、CI 上界达 +0.26，属接受零假设的 under-powered），**该测的是 corr(FM-margin, setting-gap)**。换对量后实测：guidance **r=−0.067（ns）**、**num_steps（NFE）r=−0.237（显著、CI[−0.360,−0.102]）**、speaker **r=−0.067（ns）**——即 **num_steps 是真实但温和的混淆**（单独显著），guidance/speaker 无关。决定性的**偏相关** corr(FM-margin, reward-gap | guidance, num_steps, speaker) = **partial r=−0.392，95%CI[−0.548,−0.209]，显著**：原始 Pearson −0.411 控住全部生成 knob（含 num_steps）后 → −0.392（**几乎不变**），**反相关 SURVIVES partialling**、不被 num_steps 解释。一句话：**probe_analysis 修正了 confound 测错量的问题，num_steps 温和混淆但偏相关控住**。故由「待裁决 / 未排除」**确立为 intrinsic**。**严守 C6 正确含义**：此处 intrinsic = 反相关**不是候选生成 knob 的产物**（偏相关控住了 guidance/num_steps/speaker 全部 grid 维度仍存活），**不是**「intrinsic to `L_FM`」——`L_FM` 仍是有效似然代理（open-SOAR 为证）；诊断**仍是** preference-likelihood 对齐失败 / off-manifold winner，**不回退 C6**。
- **统计严谨（全量 N=188，已收紧）**：N=188 临界 |r|≈0.143，**Pearson −0.411（p≈1e-8）与 Spearman −0.187（p≈0.01）双双显著**（n=24 时 Spearman 不显著的弱环已消除）。早期 n=24 pilot 的「winner **平均**更差（win_rate 0.33、4/24 为正、Pearson −0.496、Spearman −0.302）」是小样本 / 高杠杆点造成的**高估**，全量回归到 win_rate 0.47、44% 为正；故主结论改以**稳健的 Spearman ρ=−0.187（ρ²≈3.5%、弱单调）**为头条、**Pearson −0.411 并列标注为「杠杆放大的线性系数」**，平均效应（winner 系统性更差）不再作主张，n=24 仅留作 pilot。
- **影响（诊断重定位，非「能用配方」）**：贡献从「一个能用的 DPO 配方」转为**机理性/警示性研究**——在 **dots.tts** 上，likelihood-based DPO（FM-loss 当隐式奖励）在 automatic-metric reward 偏好呈 off-manifold 属性时是**错的工具**；**可能是架构特定的（may be architecture-specific，待 VoxCPM 等二次复现）**，故收窄到 dots.tts、不外推到「连续-latent TTS」整类。正路 = **似然对齐的偏好**（open_soar）或**非似然目标**（winners 上 reward-weighted regression / 经可微 vocoder 直接 reward 反传 / 学习式 value 头）。详见 `docs/06`。

### B-19 · X5 固定设置候选原子写崩溃：`*.wav.tmp` 让 soundfile 猜不出格式
> X5（settings-matched 复探针）要先用 `--fixed-setting` 生成「winner/loser 生成设置完全相同、仅变 seed」的候选；第一次真跑就崩在写 wav。

- **现象**：`python candidates/generate_candidates.py --fixed-setting ...` 抛 `TypeError: No format specified and unable to get format from file extension: '.../cand_fixed_0.wav.tmp'`。
- **根因**：`_write_wav_atomic` 为保证「原子写」先写**临时文件** `path + ".tmp"`（即 `cand_fixed_0.wav.tmp`）再 `os.replace` 到正式名。soundfile 默认**据扩展名猜目标格式**，临时名扩展名是 `.tmp` → 猜不出 → 报错。**网格候选当年没触发**：要么是改原子写之前的旧代码生成的、要么这批 wav 已存在被断点续跑跳过，从没真正 fresh 写过一个 `.tmp`。X5 是全新一批固定设置候选，第一次真正走到 fresh 写 → 暴露。

- **数据安全**：`run_x5.sh` 的 `trap restore EXIT INT TERM` 在崩溃时已自动把备份的网格 `candidates_index.jsonl`+`wer/sim/utmos.jsonl` 还原（日志可见「[X5] 恢复网格文件...」）→ 崩了也没污染 X6/X10 要用的网格数据。
- **教训**：**原子写「临时名 + 原子改名」与「库据扩展名推断格式」是一对天然冲突**——凡是 `lib.write(tmp_with_weird_suffix)` 都要显式传格式参数，别让库去猜 `.tmp/.part/.swp`。这类坑只在「首次真正 fresh 写」暴露，断点续跑/已存在缓存会长期掩盖它，写完务必在干净目录验证一次。

### B-20 · 实验结果未全量留存：主表被覆盖 + 分析只在 stdout（持久化补强）
> 回应「目前每次实验结果是否都有保存？」——审计发现两个会**丢结果**的缺口，本条记录修法与意义。

- **缺口①（最严重）主表被覆盖**：`results/aggregate_results.py` 原先**只遍历 `ledger.jsonl`** 的 run。而 `run_matrix.py` 每跑一批臂会重写 ledger → **下一批跑少数臂时，主表 `main_table.md` 被覆盖成只剩本次臂**。实证：X4 跑 SFT-target 几个臂后，原本 5 臂的 Table 1 被覆盖成只剩 3 臂——已评测的臂数字虽在 `results/out/*.summary.json` 里还在，但主表不显示了。
  - **修法**：汇总的 tag 集合改为 **`ledger 条目 ∪ results/out/ 下所有 *.summary.json 对应 tag`**（并集、去重、保序；排除 `*_stream.summary.json` 这种同 tag 的流式产物）。ledger 外的臂（只剩 summary.json）从 tag 名 `*_nfeN` 解析 NFE、`ckpt` 标 `(ledger 外)`。**效果：跑过的每个臂永久进主表，再不被某次 run_matrix 覆盖。**
  - **恢复动作（用户该跑一次）**：`python results/aggregate_results.py` 重出表——立刻把此前被覆盖掉的臂全部找回（它们的 summary.json 一直在）。
- **缺口②分析只在 stdout**：`alignment/probe_analysis.py`（探针统计裁决）和 `eval/diagnose_eval.py`（LJ002 聚集/发散诊断）只 `print` 到终端、不落盘——每次靠人工复制粘贴，复跑一次旧报告就没了。
  - **修法**：两脚本各加 `--out <file>`，把全部 stdout 报告**同时**归档一份(utf-8)。实现用 tee：probe_analysis 走 `_emit`（print+buffer）、diagnose_eval 覆盖内建 `print` 注入 buffer，末尾按 `--out` 决定是否落盘。**`--out` 默认 None = 只打 stdout、行为完全不变**（不破坏既有调用）。`run_x5.sh` 等驱动可后续加 `--out` 自动归档。
- **教训**：**「结果有没有保存」要分两层看**——(a) 原始/中间产物（summary.json、probe_per_pair.csv）落盘了吗？(b) **汇总/裁决产物**（主表、统计报告）是覆盖式还是累积式？本次两个缺口都在第 (b) 层：底层数字一直在，但「能直接读的那张表/那份报告」要么被覆盖、要么没落盘。**凡是「汇总多次 run」的脚本，默认应累积（读全部产物）而非只跟最近一次的索引**；凡是出裁决报告的脚本，应支持落盘归档。

### B-21 · X5 固定设置候选 immediate-EOS：逐候选容错 + 「不补救」决策 — `b2f43fb`
> X5 用 `--fixed-setting` 把同一组激进设置（num_steps=10/guidance=1.2/speaker=1.5）套到所有 prompt 重生成候选；某些 prompt 在该固定设置下不产音，单候选崩不该炸整轮（数 GPU-h）。

- **现象**：`✓ 共 1502 候选（新生成 0，复用 1502，失败 2）`；`⚠️ 生成失败 2/2 本次尝试（100.0%）；占全网格 2/1504=0.13%；0 个 prompt 零候选`。
- **根因**：dots.tts 是 flow-matching 连续-latent TTS，对某些 `(文本, 参考, 设置, seed)` 组合**立即预测 EOS、不产 payload latent** → `RuntimeError: produced no payload latents…`。`--fixed-setting` 把同设置硬套全 prompt 时更易撞上（个别 prompt 在该固定设置下不适配），且 `num_steps=10` 偏低、退化概率更高。
- **修法**（`generate_candidates.py`）：逐候选 `try/except`，失败则记账（`_generation_report.json` 的 `failures[]` 存 fid/k/seed/设置/error）+ 打一行 ⚠️ + `continue`，**不炸整轮**。下游 `build_preference_pairs` 已 `len(items)<2: continue`，零/单候选 prompt 自动不成对（X5 实测仍 `188 对/188 prompt`，一对没少）。
- **失败率本身是结果**：`--fixed-setting` 下的 immediate-EOS 率反映「该固定设置对哪些 prompt 不适配」，落盘存证（提示口径修正见 §0 #34 / D-8）。
- **决策——不补救（重要）**：**不靠调 `num_steps/guidance/speaker` 把失败候选救活**——那会破坏 X5 的 settings-matched 不变式（winner/loser 必须设置完全相同、**只许变 seed**），等于自污染要证的 intrinsic。唯一合规救法是**换 seed 重试**（X5 本就变 seed），但收益极小（补回 0.13%）、且 immediate-EOS 多由 `(prompt,设置)` 决定、换 seed 未必成；本次 0.13%、0 空 prompt、188 对不少 → **决定不补救**（见 §F）。
- **教训**：生成类管线对**单样本失败**要逐样本容错（崩一条 ≠ 崩整轮），并把失败率当**一等结果**落盘；「补救失败样本」前先问会不会破坏实验不变式——配对设计里**只有被显式允许变的维度（seed）才能动**。

### C-6 · `unauthenticated requests to the HF Hub` 提示（良性）
- **现象**：下载 SpeechBrain ECAPA / dots.tts 权重时打印 `Warning: You are sending unauthenticated requests to the HF Hub. Please set a HF_TOKEN ...`。
- **是什么**：huggingface_hub 提示「未登录，受匿名速率限制」。下载**照常成功**，只是慢一点/有速率上限。
- **处理**：不用管；若下载大模型频繁限速，可 `export HF_TOKEN=...`（HF 账号 token）提速。**不影响结果**。

### C-5 · 保存 checkpoint 时的 `Removed shared tensor` 提示（良性）
- **现象**：`accelerator.save_state` 打印
  `[RANK 0] Removed shared tensor {...vocoder...lstm..., core.llm.lm_head.weight} while saving. This should be OK...`。
- **是什么**：safetensors 保存时检测到**权重共享/绑定**——`core.llm.lm_head.weight` 与词嵌入 tied、vocoder 的 LSTM 权重内部共享存储；它把重复的去掉只存一份。**它自己也说 "This should be OK"**，reload 时会自动重建。
- **处理**：**不用动**。属正常的 tied-weights 行为。
- **教训**：tied weights（lm_head↔embedding）在保存时被 safetensors 去重是常态，不是数据丢失。

### C-4 · 模型加载期的良性 warning 已统一静音（`common.py`）
跑 `check_fm_loss.py` / 训练 / 推理时，加载 dots.tts 模型会打印若干良性 warning。已在 `common.py` 顶部统一处理（每个脚本都 import 它）：
1. `model of type dots_tts to instantiate ''`（transformers 注册噪声）→ `TRANSFORMERS_VERBOSITY=error` 压掉。
2. `tokenizer ... fix_mistral_regex=True`（见 C-3，**绝不能真改**）→ 同上压掉。
3. `weight_norm is deprecated`（**dots.tts 的 BigVGAN vocoder** 用了旧 torch API，与我们无关）→ `warnings.filterwarnings` 针对性忽略。
4. `Download complete: 0.00B`（huggingface_hub 对已缓存文件的进度条）→ **保留不压**（避免连真实大文件下载进度一起隐藏）。
- 全用 `setdefault`/针对性过滤，用户可覆盖（`export TRANSFORMERS_VERBOSITY=warning` 看全部）。
- **教训**：良性 warning 统一在共享模块（`common.py`）静音，比每个脚本各写一遍干净；但**只压不影响结果的，且保留真实下载进度**。

### C-3 · 模型加载期的两条提示（**保持原样，勿改**）
跑候选生成 / 自检时，dots.tts 加载会打印：
1. `You are using a model of type dots_tts to instantiate a model of type ''`
   - dots.tts 自定义架构在 transformers 注册的样板噪声，**无影响**。
2. `tokenizer ... incorrect regex pattern ... set fix_mistral_regex=True`
   - **是什么**：transformers 觉得 dots.tts 的 tokenizer 正则不符合 Mistral「标准」。
   - **为什么不能改**：dots.tts 就是用这个 tokenizer **原样训练**的；我们用 `model.tokenizer`（同一个）给候选/训练文本分词 → **与模型训练时一致才是对的**。设 `fix_mistral_regex=True` 反而会让分词偏离模型预期、**损坏结果**。
- **教训**：**「修复某 warning」不等于「让结果更对」**——有时按 warning 建议改反而是错的。判断标准永远是「是否与模型训练时一致」。

### C-7 · `Loading weights: 1259/1259` 不是候选数，是模型权重张量数（良性误读）
- **现象**：X5 step 2 打分一开始刷 `Loading weights: 100%|...| 1259/1259 [00:00<00:00, 6800it/s]`（有时连刷两条），对照上面「1502 候选」困惑：为什么是 1259？
- **是什么**：这是 **WER 用的 Whisper-large-v3 把自己的权重张量装进显存**的进度条，`1259` = 该模型的**命名权重张量个数**（架构固定：≈ 4 conv + enc/dec 各 32 层 + 末 LN + 位置/词嵌入 ≈ 1259），与候选数（1502）**毫无关系**。连刷两条是 transformers **分两趟**过这些张量（读 checkpoint → 转 fp16/搬 GPU），瞬时（数千 it/s）、无害。
- **为什么会误以为卡死**：这条秒过之后才是**真正耗时**的那段——Whisper 逐条转写 1502 候选，**旧代码全程无输出**（已修，见 §0 #33 / D-7：现有 `WER/EN Whisper(bs=…)` 进度条）。候选数只在末尾以 `✓ WER 打分 1502 条` 出现。
- **处理**：**不用管**。看到 `1259` 不必对应任何数据量；要看打分进度看新加的 `WER/EN`/`UTMOS`/`SIM` 进度条。

### D-6 · 审计加固 pass：12 路对抗核验「实验设计/选择/参数是否合理通顺」（**0 blocker，全 reporting-only**）
> 本条是**主动改进**（**非报错**）——投稿前对整条证据链做一轮敌意自审并留痕。决策体例与三类动作去向见 `docs/02` **ADR-12**；机理与全部数字见 `docs/06`；逐条审稿线程见 `docs/07`。**与前面 A–D 各坑的区别**：A/B/C 是「跑出来才暴露、必须修」的真问题，D-1~D-5 是「关乎正确性的主动接缝修正」，而 **D-6 是『方法本身没问题、只补防御层』的核验记录**——它不改方法、不改参、不改任何已报结论数字。

- **做什么**：对 ADR-10/11 立稳的三支柱——**preference-likelihood 对齐失败**、**intrinsic 确立**（偏相关 partial r=−0.392，CI[−0.548,−0.209]）、**头条 Spearman ρ=−0.187**（CI[−0.335,−0.036]）——做 **12 路对抗式核验**：逐条尝试推翻**实验设计/选择/参数本身**是否合理通顺（**不是**找运行期 bug）。
- **怎么做（12 路线程 + 各自落点；线程命名同 `docs/07`/`docs/02` ADR-12）**：统计 **S1–S5**、devil's-advocate **D1–D3**、project **P2**、confound **C1/C2**，外加贯穿全篇的 **C6** 两层切分 = 12 路。
  1. **S1 TWO-STATS**：「头条 Spearman 小、却又用 Pearson 偏相关 → 偷换大数」→ 二系数永远**同报**、回答**不同问题**（头条 Spearman 抗高杠杆点；intrinsic 用 Pearson-族偏相关控混淆），杠杆已由 trim/LOO/高-gap 独立控住 → **A 措辞**。
  2. **S2 FDR-VENUE**：「~14 个相关检验 → 多重比较未校正」→ 合法 FDR 场所是 **>100-CI 的消融网格**（`main_table`/`reward_hacking`/Table 1–3），不是单方向稳健性检查；偏相关是唯一**预设确证终点**（Bonferroni/14 后 CI 上界仍 <0）→ **A 措辞 + C 脚本**（`aggregate_results.py` B5）。
  3. **S3 X1-DOWNGRADE**：「win_rate 0.47 大半 near-tie → 反相关是平局稀释假象」→ 高-gap 分层（两档阈值均**预设、全报**）：top-50% ρ=**−0.407**（n=94）、top-25% ρ=**−0.440**（n=47），CI 均排除 0、约 2× 全集 → **B 硬数字**（但因截取扩大动态范围，**不**主张「真有质量差时效应更强」，binomial p=0.093 是独立符号检验、不作相关证据）。
  4. **S4 LINEAR + HONEST-CONFOUND**：「偏相关只做线性残差化 / num_steps 混淆被你藏了」→ 措辞软化为「**线性**控住生成 knob」、决定性非参控制留给 X5 settings-matched；并**主动公布** num_steps r=**−0.237**（CI[−0.360,−0.102]）、控混淆后系数几乎不动（−0.411→**−0.392**）→ **A 措辞 + B 硬数字**。
  5. **S5 ATTENUATION**：「K=16 MC 噪声大 → 反相关是噪声」→ K=16 测量噪声与独立计算的 reward_gap 无关，经典 regression dilution 只把 |相关| 向 0 衰减 → Spearman −0.187 / partial −0.392 是**保守下界**（disattenuation 只增不减）；且高-gap 子集反而更强（与噪声伪影预测相反）→ **B 硬数字**（写成 rebuttal 正面论据）。
  6. **D1 NEAR-TIE-SPLIT**：显式区分 **FM-margin near-tie**（真实、win_rate 0.47、已降级为非头条）≠ **reward-gap near-tie**（实测 **0%**、中位 **1.39**，对被充分分开）→ **A 措辞**。
  7. **D2 SIM-HEDGE**：per-component 的 **SIM_gap −0.676** 来自单说话人 LJSpeech **近-ceiling、判别力弱**的 SIM（可能由少数真有 SIM 差的对带杠杆）→ 承重证据放更具判别力的 **UTMOS_gap −0.597** 与方向明确的 **WER_gap +0.412**，SIM 降级为带 hedge 的次要佐证 → **A 措辞 + B3 杠杆诊断**。
  8. **D3 STEP-BUDGET**：「open-SOAR(600 步) vs sft(1500 步) 步预算不同 → 改善对比被混淆」→ 由 X4 `sft_groundtruth@1500`（on-manifold、同 SFT 目标、仅变 target 流形位置）在跑出后消除；佐证 `dpo_multiobj` 仅 600 步即崩、唯一 1500 步的 sft 居中 → 步数与崩坏非单调 → **B（数据待 GPU）**。
  9. **P2 WEIGHT-SIMPLEX + SOAR-NOISE**：「reward 权重 (0.4,0.3,0.3) 没扫 / `soar_noise_scale=0.5` 没 ablation」→ (−WER)/SIM/UTMOS **三轴各自**都与 FM-margin 反相关、聚合是非负加权和 → 头条符号在整个**权重单纯形**上不可翻（per-component = 检验极端顶点、严格强于扫描）；soar_noise 只标定 loser off-manifold 程度、winner 恒 on-manifold → 只影响改善「幅度」、**不**威胁方向 → **A 措辞**。
  10. **C1（confound 测错量）**：已在 B-17 / `docs/06` §6.1 修——旧 `inspect_guidance_confound.py` 测的是 corr(reward-gap, setting-gap)，**该测** corr(FM-margin, setting-gap)，换对量后由 `probe_analysis.py` 裁决 → 已闭合。
  11. **C2 OPEN-SOAR-REFRAME**：「`L_FM` 有效似然代理的证据搭在 open-SOAR 饱和上」→ open-SOAR by-construction（clean-vs-加噪 loser 易分）只证「机制可用 + optimizer 正常」、**不**独立证 `L_FM` 是忠实 NLL 上界 → 保留「似然**启发**代理」caveat，决定性独立锚改挂新实验 **X14**（`probe_lfm_validity.py`）→ **A 措辞 + C 独立锚**。
  12. **C6（intrinsic ≠ intrinsic-to-`L_FM`）**：守约——此处 intrinsic = 「不是生成 knob 造的」（偏相关控住 guidance/num_steps/speaker 全部 grid 仍存活），**不是** 「intrinsic to `L_FM`」（`L_FM` 仍有效，open-SOAR 为证）；诊断仍是 preference-likelihood 错配、不回退 → **A 措辞**（贯穿全篇）。
- **核验结论（最重要）**：**0 blocker / 0 真缺陷 / 0 改参**——12 路全部落「**reporting-only**」（措辞软化、补**已算出**的硬数字、或加可选独立锚脚本），**无一要求改 JSONL schema、改「四前向共享-(x0,t)」契约、改奖励权重 (0.4,0.3,0.3)、或推翻任一已报结论数字**。即：**方法是对的，要加固的是「怎么把它讲清楚/防御住」，而非方法本身**。
- **为什么这能 pass：多条标准敌意攻击的方向其实是反的（攻击点恰是保守/诚实的证据）**：
  1. **「Spearman 比 Pearson 小很多 → 你挑大的报」→ 反**：头条本就领**保守**的 Spearman **−0.187**（Pearson −0.411 仅并列标注为「杠杆放大的线性系数」）——挑小的、抗杠杆的那个当头条，是保守不是夸大。
  2. **「num_steps 混淆你 → 藏起来了」→ 反**：我们**主动公布** num_steps r=**−0.237**、再展示控住后系数几乎不动（−0.411→−0.392）——**藏掉它才是作弊**，亮出来再证其无害是诚实。
  3. **「K=16 太少 → 信号是噪声」→ 反**：K=16 测量噪声经典 regression dilution 只把 |相关| 向 0 **衰减** → 报告的 −0.187/−0.392 是真值的**保守下界**，更多 draw 只会更强、不会翻号。
  4. **「win_rate 0.47 ≈ 抛硬币 → 没有效应」→ 反**：FM-margin 平均≈0 大半是 **near-tie 数据产物**（已降级、不作独立证据）；而 reward-gap 侧实测 **0% 近平局**（中位 1.39，对被充分分开），核心证据是**反相关**且在高-gap 子集上**最强**（≈2×）。
- **产出（A/B/C 三类，与硬约束「只增措辞/硬数字/新脚本」一一对应）**：
  - **A 透明度措辞**：上述 8 条 A-类（LINEAR/OPEN-SOAR-REFRAME/SIM-HEDGE/WEIGHT-SIMPLEX/SOAR-NOISE/TWO-STATS/FDR-VENUE/NEAR-TIE-SPLIT）→ `docs/02` ADR-12 + `docs/06`/`docs/08`(PAPER)/`docs/07`(rebuttal)。
  - **B CPU 硬数字**：`alignment/probe_analysis.py` 加 **B1 Spearman 偏相关 / B2 Bonferroni/14 / B3 SIM_gap 杠杆诊断**（+B4 NFE²、B6 split-half 解衰减）；全 reporting-only、`_boot_ci` 加 `alpha` 默认值不动既有任何系数/CI（登记见 §0 第二轮表上方 surfacing 注）。
  - **C X14 独立锚**：`alignment/probe_lfm_validity.py`（typicality：真实录音 vs reward-winner 的配对 `L_FM`）+ `results/aggregate_results.py` 的 FDR/Bonferroni 扩展（已登记 §0 第二轮表）。
- **当前状态（如实标注）**：A/B = 措辞 / **已算出**数字的 surfacing，不改任何已报结论；C（X14、FDR 脚本）为**脚手架/计划态，本机仅 `py_compile`/`bash -n`、结果待 GPU，不得记为「已完成/有结论」**（X14 typicality 首选、ODE-NLL 子协议可行性〔需核实〕，结果待出、不得预判方向）。
- **教训**：**投稿前的价值不只在「修真 bug」，更在「把已诚实的设计的透明度，补到敌意审稿误读不了」**——把对自己不利的量（num_steps 混淆 −0.237、win_rate 0.47、SIM 近-ceiling）**主动亮出**再证其无害，本身就是保守诚实的最强信号；而当 12 路敌意攻击有多条**方向是反的**（攻击点恰好是你最保守的选择）时，正确的动作是**把这层「为什么反」讲明白**，而不是反射式地去改方法/参数（改它们反而引入新的未对齐混淆，cf. ADR-6 LoRA-vs-full 三重混淆教训）。

### D-7 · 打分阶段可观测性 + SIM 参考嵌入缓存（`4c63c02`）
> 回应「X5 跑到 2/5 卡住了吗」——其实没卡，是 Whisper-large-v3 静默转写上千候选要数分钟、全程无输出（旧代码三脚本只在结束打一行 ✓）。本条「看得见」+「少算一半参考前向」一起做，**不改任何指标数值/行序**（3-lens 对抗式静态核验确认 values/order identical、0 blocker）。

- **做什么**：`score_wer.py`/`score_utmos.py`/`score_sim.py` 三脚本加 `tqdm` 进度条（缺 tqdm 时降级恒等迭代、不崩、不改结果）；`score_wer` EN 路径改**逐批**喂 Whisper（同 `batch_size`、同 `generate_kwargs`，与单次整列调用逐条等价——Whisper 每条 pad 到 30s、逐样本独立贪心解码，批边界不改文本）；`score_sim` 给 ecapa/wavlm 两后端各加**路径→嵌入缓存**。
- **为什么 SIM 缓存有效**：同一 prompt 的 K 个候选共享同一条 `prompt_audio`，旧代码逐候选把参考音频**重复编码 K 次**；缓存后参考只编码一次 → 前向次数从 `候选数+候选数` 降到 `候选数+唯一参考数`，约省一半 GPU 前向（候选音频路径唯一、缓存只占 ~MB 级显存可忽略）。
- **对实验意义**：纯可观测/性能，**不动后端（large-v3/ecapa）、不动默认、不动数值**；X5/主网格打分阶段从「看似卡死」变「带 ETA 的进度条」，顺手砍掉 SIM 重复前向。
- **教训**：多分钟、无中途输出的重推理段要给进度条（否则看着像卡死，见 §0 #33 / C-7）；配对数据里「多候选共享同一参考」是常见冗余，按路径缓存嵌入是零风险提速。

### D-8 · 候选生成失败提示加「占全网格」口径（`1b794df`）
> 回应「为什么 1502 候选会有 2 个失败、还显示失败率 100%」——`failure_rate` 分母只算「本次真生成尝试」，命中缓存时只补几个候选、失败 2/2 就显示 **100%**，看着像全崩。

- **现象（误导）**：`⚠️ 生成失败 2/2（失败率 100.0%）`——分母 `= n_gen + n_fail`（复用不计入），缓存全命中时分母极小、易虚高到 100%；实为占全网格 `2/1504≈0.13%`。
- **修法**（`generate_candidates.py`）：失败提示**同时**打印两种口径——`生成失败 N/attempted 本次尝试（rate）；占全网格 N/grid_total=rate2`；`_generation_report.json` 增加 `grid_total`、`failure_rate_grid` 字段，旧 `failure_rate`（本次尝试口径）**保留兼容**（已 grep 确认无下游读它：`aggregate_results`/`diagnose_eval` 读的是 `_synthesis_report.json` 同名字段、互不相干）。
- **对实验意义**：失败率口径不再误导；真实规模看 `failure_rate_grid`（本次 0.13%）。失败成因与「不补救」决策见 B-21。
- **教训**：**比率类输出务必标清分母口径**——「本次尝试」vs「全量网格」是两个数，缓存场景下前者会失真；改报告字段前先 grep 确认没有同名字段的别处消费者。

## E. 通用经验总结（给后来者）

1. **设计期只能语法检查，运行期错误必然在 GPU 机器上才暴露**——所以「本机 `py_compile` 通过」≠「服务器能跑」。早跑小样冒烟（`--limit`）尽快触发真问题。
2. **外部依赖的「名字、版本、API」三者都要核实**：speechmos 名字像 UTMOS 全家桶其实没有 utmos（B-3）、版本臆测 `>=1.0.0` 不存在（A-2）。
3. **优先复用已装的重依赖**：WER 用 transformers（已装）而非 openai-whisper（B-1）；UTMOS 用 torch.hub 而非再引包（B-3）。
4. **契约值从模型派生、绝不硬编码**：`patch_size` 真值与假设不符时代码自动适配（D-3）。
5. **warning 分两种**：性能/弃用类（如 sequential-on-GPU、torch_dtype）值得真改（C-1）；行为播报类（SuppressTokens、BPE 清空格）消音即可，且**有的按建议改反而错**（C-3 的 fix_mistral_regex）。判断基准永远是「**是否与模型训练时一致**」。
6. **接缝要有自检**：`check_fm_loss.py` 把「方法能否成立」的命门（共享-RNG 决定论）做成可一键验证的 PASS/FAIL，开训前必跑。
